El proyecto en una imagen

Es un monorepo didáctico: una base mínima ya funcionando para que practiques features reales sin perder días en infraestructura. El alcance es deliberadamente pequeño; lo que falta (CRUD completo, validaciones, modales, paginación, otra entidad…) son retos para ti.

Backend

Java 21, Spring Boot 3, Maven. Endpoint de ejemplo: GET /api/employees. Swagger expuesto en el puerto 8080.

Frontend

Angular 17+, standalone components, signals y SCSS. Lista de empleados consumiendo el API real.

La documentación canónica del repo vive en README.md, en la misma carpeta que este manual.

— 03

Objetivos de aprendizaje

  1. Entender el flujo end-to-end: desde la petición HTTP en Angular hasta la persistencia en MongoDB.
  2. Leer código ajeno: paquetes employees en back y features/employees en front como referencia de estilo.
  3. Ampliar el producto por capas: DTO, validación, servicios, rutas, formularios reactivos, manejo de errores.
  4. Practicar calidad: tests (JUnit / Karma), mensajes de error claros, decisiones de diseño documentadas.
— 04

Consejos si estás empezando

  • Un cambio a la vez: arranca el stack, confirma que ves los 10 empleados de ejemplo, y sólo entonces añade una feature.
  • Reproduce antes de arreglar: anota el error exacto, el endpoint y el payload. La mitad de los bugs son URL, CORS o datos.
  • Lee el stack trace y la consola de red: en el navegador, pestaña Network; en Java, el log de Spring.
  • Commits pequeños: uno por tarea lógica facilita revertir y pedir revisión.
  • Pide feedback con contexto: “quiero POST /employees, me devuelve 400 con este JSON” es mejor que “no funciona”.
— 05

Herramientas recomendadas

IntelliJ IDEA

Es el IDE que usamos en el proyecto para Java y el backend: prioriza IntelliJ ahí. Activa annotation processing e instala el plugin de Lombok para que compile sin avisos raros.

Visual Studio Code

Para Angular y el frontend se recomienda Visual Studio Code: integración muy buena con TypeScript, plantillas HTML, ESLint y depuración. Instala la extensión oficial Angular Language Service (y, si quieres, el Extension Pack for Java sólo si también editas Java desde VS Code; para el back sigue siendo preferible IntelliJ).

Postman

Colecciones para probar la API: GET, POST, PUT, PATCH y DELETE, cuerpo JSON y códigos de respuesta antes de tener el formulario en el front.

Terminal

En Windows elige lo que te resulte más cómodo: PowerShell (integrado, útil para Get-NetTCPConnection y puertos) o Git Bash (sintaxis tipo Linux, como en muchos tutoriales). Tres terminales: Docker, backend y frontend.

Rancher Desktop

Interfaz para contenedores; alternativa a Docker Desktop. Desde la raíz del proyecto:

docker compose up -d

Sourcetree (o Git en consola)

Si te abruma la línea de comandos, Sourcetree te da una vista gráfica de ramas, commits y diffs. Si prefieres consola, los comandos básicos sobran. Lo importante es ver siempre qué vas a subir.

— 06

Trabajar con Git sin miedo

Regla de oro del repo: nunca commitees directamente en main. La rama principal queda “virgen” para que cualquiera que clone el proyecto se encuentre la base estable. Tú vives en ramas de feature.

Flujo recomendado

  1. Actualiza main antes de empezar: git checkout main y git pull.
  2. Crea una rama por tarea: git checkout -b feature/employee-detail. Un nombre, un objetivo.
  3. Commitea en pequeño: un cambio lógico = un commit. Mensaje en imperativo y claro.
  4. Sube y abre Pull Request: git push -u origin feature/... y revisa el diff antes de pedir merge.
  5. Tras merge, borra la rama local y remota para no acumular ruido.

Comandos que más usarás

git status                    # qué ha cambiado
git diff                      # qué exactamente
git add .                     # preparar todo
git commit -m "mensaje"       # confirmar
git push                      # subir al remoto
git pull --rebase             # traer cambios de main sin merge sucio
git log --oneline --graph     # historia visual rápida

Estilo de mensajes de commit

Imperativo, en presente, breve y centrado en el qué:

  • feat: añade endpoint GET /api/employees/{id}
  • fix: corrige error 500 al recibir email vacío
  • refactor: extrae mapper EmployeeMapper
  • test: cubre EmployeeService.findById con caso no encontrado
  • docs: explica el flujo de Git en el manual
  • chore: actualiza dependencias del frontend
i

Antes de commitear, abre Sourcetree (o ejecuta git diff --staged) y revisa línea a línea: te ahorra explicar bugs después.

!

Si por error commiteaste en main sin subir todavía: git branch feature/x, git reset --hard origin/main, git checkout feature/x. Pregunta antes de hacer --force en remoto.

— 07

Stack backend y frontend

Una vista rápida de qué hay en cada lado antes de meterte en los retos.

Spring Boot 3 + Java 21 + Maven. Capas típicas en el paquete employees/:

  • Entity + repositorio (Spring Data MongoDB): cómo se guarda el documento.
  • Service: reglas de negocio y orquestación.
  • Controller REST: rutas, códigos HTTP, validación de entrada.
  • DTO + mapper: no expongas siempre el modelo interno tal cual.
  • GlobalExceptionHandler: respuestas de error homogéneas.
  • Seed: datos iniciales si la colección está vacía al arrancar.

Documentación API: Springdoc / Swagger. Config: application.yml (Mongo URI, CORS en dev).

Angular 17+ con componentes standalone, signals para estado reactivo y SCSS.

  • app.config.ts: HttpClient, interceptor de errores, token API_URL.
  • features/employees/: modelo, servicio que llama al API y página de lista.
  • core/: lógica transversal (interceptors, tokens).
  • shared/: hueco para componentes reutilizables a medida que crezcas.

Rutas y nuevas pantallas se registran en app.routes.ts. Tests de ejemplo: componente + servicio con HttpTestingController.

— 08

Retos paso a paso

Deberes mínimos antes de subir de nivel: levantar los tres procesos sin ayuda, localizar dónde se define la URL del API y ejecutar los tests de back y front al menos una vez.

Cada reto está plegado. Ábrelo y verás pistas para abordarlo tanto desde el backend como desde el frontend. No son soluciones cerradas: son atajos para que no te quedes en blanco.

01Detalle de empleado GET /api/employees/{id} y ruta /employees/:id en el front.
Backend
  • Añade @GetMapping("/{id}") en EmployeeController.
  • El repositorio ya devuelve Optional<Employee>; si está vacío, lanza una excepción y deja que GlobalExceptionHandler la traduzca a 404.
  • Mapea la entidad a DTO antes de devolverla.
  • Test con @WebMvcTest: caso encontrado (200) y caso no encontrado (404).
Frontend
  • Crea EmployeeDetailComponent standalone en features/employees/pages/.
  • Registra la ruta { path: 'employees/:id', component: EmployeeDetailComponent } en app.routes.ts.
  • Lee el id con inject(ActivatedRoute) y route.snapshot.paramMap.get('id').
  • Añade getById(id) al servicio; gestiona estados cargando, error y no encontrado con signals.
02Alta de empleado POST /api/employees con validación y formulario reactivo en /employees/new.
Backend
  • Endpoint @PostMapping que recibe un DTO anotado con @Valid.
  • En el DTO: @NotBlank en nombre/apellido/posición, @Email en email.
  • Maneja email duplicado capturando DuplicateKeyException y devolviendo 409 Conflict.
  • Devuelve 201 Created con la cabecera Location apuntando al recurso nuevo.
Frontend
  • Importa ReactiveFormsModule en el componente standalone.
  • Construye el formulario con FormBuilder y los validadores Validators.required y Validators.email.
  • Muestra los errores de cada campo sólo cuando esté touched o dirty.
  • Tras el create(), redirige al detalle o a la lista; si el back devuelve 409, muestra mensaje claro.
03Edición y borrado PUT y DELETE en el back; pantalla de edición y confirmación en el front.
Backend
  • @PutMapping("/{id}") devuelve 200 con el recurso actualizado, o 404 si no existe.
  • @DeleteMapping("/{id}") devuelve 204 No Content en éxito.
  • En el service, comprueba existencia antes de actualizar/borrar y devuelve un error semántico claro.
  • Añade un test por caso: éxito, no encontrado y validación fallida.
Frontend
  • Reutiliza el formulario del alta en modo edición: precarga los valores con patchValue().
  • Para borrar, empieza con un confirm() nativo y luego sustitúyelo por un modal propio.
  • Después del borrado, refresca la lista o navega con router.navigate(['/employees']).
  • Desactiva los botones mientras la petición está en vuelo (signal<boolean> saving).
04Filtros y paginación Query params en el back; buscador y paginador en el front.
Backend
  • Acepta @RequestParam(required = false) String firstName, position, etc.
  • Usa Pageable de Spring Data: el repo puede devolver Page<Employee> con totales y nº de páginas.
  • Para filtros sencillos, métodos derivados (findByFirstNameIgnoreCase…); para combinados, @Query o Example.
  • Devuelve metadatos de paginación (page, size, totalElements).
Frontend
  • Guarda filtros y página actual como signal() y deriva la query con computed().
  • Aplica debounceTime(300) al input de búsqueda (con toObservable o directamente con FormControl).
  • Empieza con un paginador simple: botones anterior / siguiente y contador “3 / 12”.
  • Sincroniza la URL con los filtros si quieres compartir enlaces (queryParamsHandling: 'merge').
05Segunda entidad relacionada Modela Department y relaciónalo con Employee.
Backend
  • Decisión consciente: embed (guardar nombre del depto en el empleado) o referencia (departmentId). Documenta el porqué.
  • Crea entidad, repositorio, service y controlador siguiendo la misma estructura que employees.
  • Endpoint para listar departamentos (GET /api/departments) que el front usará en el selector.
  • Si vas por referencia, piensa en qué hacer si borras un departamento con empleados (¿error 409?).
Frontend
  • Crea features/departments/ con su modelo y servicio.
  • En el formulario de empleado, añade un <select> que cargue departamentos al inicializar.
  • En la tabla de empleados, muestra el nombre del departamento (resuélvelo en el back o crúzalo en el front).
  • Reutiliza tipos compartiendo el modelo (Department) entre features vía shared/ si crece.
06Mejoras transversales Toasts, más tests, perfiles dev/prod y autenticación.
Backend
  • Perfiles: application-dev.yml y application-prod.yml; activa con SPRING_PROFILES_ACTIVE.
  • Spring Security + JWT: filtro que valide el token, UserDetailsService sencillo en memoria para empezar.
  • Sube cobertura: tests de happy path y casos límite (validación, 404, 409).
  • CORS distinto por perfil: en prod sólo orígenes conocidos.
Frontend
  • Servicio de toasts global: un signal<Toast[]> y un componente que los pinte; el interceptor los dispara.
  • AuthGuard con CanActivateFn que comprueba el token en localStorage.
  • Interceptor que inyecte Authorization: Bearer ... en cada petición.
  • Tests con HttpTestingController para asegurar que el interceptor mete la cabecera.
!

No hay solución oficial a propósito: la práctica consiste en implementar y comparar después en revisiones o con un mentor.
